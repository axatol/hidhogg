# Scroll reporting and SmartShift feasibility

Research date: 20 October 2026. Scope: MX Master 3S over Logi Bolt; static upstream and product documentation, plus existing local probe summaries. No device setting was changed or tested for this report.

## Finding

Native HID++ feature paths exist for changing wheel-report resolution and SmartShift settings when the selected connection advertises them. Strict line-step movement or disabling animation in macOS applications remains unproven. Keep device report resolution separate from the wheel's mechanical ratchet/free-spin policy and from how applications animate scroll events. A low-resolution mode may produce coarser input, but does not guarantee whole-line movement.

## Device reporting: HID++ 0x2121

Logitech's HID++ 2.0 protocol resolves a feature ID through each device's feature table before calling its functions; do not assume a fixed feature index. The upstream Solaar implementation identifies feature `0x2121` as `HIRES_WHEEL`. Its get-mode request is function 1 (`0x10`) and set-mode is function 2 (`0x20`); function 3 (`0x30`) reads the ratchet-switch state. [Logitech HID++ 2.0 protocol](https://github.com/Logitech/cpg-docs/blob/master/hidpp20/README.rst#L221-L231), [Solaar feature list](https://github.com/pwr-Solaar/Solaar/blob/master/docs/features.md), [Solaar decoder](https://github.com/pwr-Solaar/Solaar/blob/master/lib/logitech_receiver/hidpp20.py#L1876-L1899)

The mode byte uses bit 0 (`0x01`) for native HID versus diverted HID++ event routing, bit 1 (`0x02`) for low/high-resolution reporting, and bit 2 (`0x04`) for inversion. Solaar reads and writes resolution by masking only `0x02`; it treats capability flag `0x08` as inversion support and `0x04` as ratchet-switch support. It does not identify a separate high-resolution capability bit in that parser. [Solaar settings](https://github.com/pwr-Solaar/Solaar/blob/master/lib/logitech_receiver/settings_templates.py#L426-L454), [Solaar capability/mode parsing](https://github.com/pwr-Solaar/Solaar/blob/master/lib/logitech_receiver/hidpp20.py#L1876-L1899)

For this app, preserve the complete observed mode byte and change only `0x02`; retain direction bit `0x04` and routing bit `0x01`. Keep the existing response validation (`mode & 0xF9 == 0`, reserved response byte zero) and per-connection feature discovery. Only offer the picker for a successfully discovered and validated `0x2121` mode. The existing implementation's bit-preserving direction write and cleanup ownership model are the appropriate local seam to extend. [Current wheel controller](../app/Sources/LogitechBolt/BoltController.swift#L475-L535), [slice contract, decisions 33–37](logitech-slice-contract.md#L25-L29)

## SmartShift: physical wheel mode

Logitech describes MX Master 3S SmartShift as switching the MagSpeed wheel from line-by-line ratchet to free-spin when the wheel turns faster; Options+ can disable automatic shifting and adjust its sensitivity. These are changes to the wheel's physical mode, distinct from the `0x2121` resolution bit. [Logitech MX Master 3S for Mac guide](https://support.logi.com/hc/en-ca/articles/8335872639767-Getting-Started-MX-Master-3S-for-Mac)

Solaar's upstream setting definitions provide the bounded protocol mapping:

- Legacy SmartShift feature `0x2110`: read function 0 (`0x00`), write function 1 (`0x10`). Its fixed-mode choices are raw mode 1 = free-spin and 2 = ratcheted. Its UI sensitivity range is 1–50; the writer sends mode 0 with the selected threshold and maps the UI maximum 50 to raw threshold `0xFF` (the source describes the maximum as always ratcheted). The source does not establish whether mode 0 means automatic or “leave mode unchanged”; do not assign it an Auto meaning without a separate protocol or device result. [Solaar settings](https://github.com/pwr-Solaar/Solaar/blob/master/lib/logitech_receiver/settings_templates.py#L623-L667)
- Enhanced SmartShift feature `0x2111`: read function 1 (`0x10`), write function 2 (`0x20`), with the same sensitivity mapping and the same mode-value uncertainty. The optional ratchet-torque setting has range 1–100 and is created only when the feature's capability bit 0 is present. Defer torque from the first UI slice. [Solaar enhanced settings and capability gate](https://github.com/pwr-Solaar/Solaar/blob/master/lib/logitech_receiver/settings_templates.py#L670-L703)

The intended native UI is a `Standard`/`High-resolution` report picker plus `Automatic (SmartShift)`/`Ratchet`/`Free-spin` wheel behavior, with sensitivity shown only for Automatic. The UI concept is clear, but exact HID++ command semantics for selecting Automatic remain unknown; keep mode and threshold as separate fields until verified. If retaining Solaar's 1–50 scale, label 50 as “always ratcheted” rather than an ordinary threshold. Discover `0x2110`/`0x2111` and their usable functions on the selected device before enabling those controls; product documentation and upstream support do not prove that a particular Bolt session accepts these writes.

In Automatic mode, the wheel's observed ratchet/free-spin state can change during normal scrolling. If the app reads the `0x2121` ratchet-switch state, treat it as transient observed state, separate from the configured SmartShift mode and threshold; a transition alone is not evidence that another writer changed the setting. The exact target-device state/notification behavior still needs hardware verification. [Logitech MX Master 3S guide](https://support.logi.com/hc/en-ca/articles/8335872639767-Getting-Started-MX-Master-3S-for-Mac), [Solaar ratchet-state reader](https://github.com/pwr-Solaar/Solaar/blob/master/lib/logitech_receiver/hidpp20.py#L1876-L1899)

## Device input versus on-screen motion

Apple defines `hasPreciseScrollingDeltas` as indicating whether an `NSScrollWheel` event carries precise deltas. Apps interpret `scrollingDeltaY` differently depending on that value: non-precise deltas are multiplied by a line or row height; precise deltas are used as the scroll amount. This is app-facing event semantics, not a promise about visual animation. It follows that the device's resolution toggle cannot guarantee line snapping or disable animation across macOS applications. That conclusion is an inference from Apple's event contract. [Apple `hasPreciseScrollingDeltas`](https://developer.apple.com/documentation/appkit/nsevent/hasprecisescrollingdeltas), [Apple `scrollingDeltaY`](https://developer.apple.com/documentation/appkit/nsevent/scrollingdeltay)

Static Options+ instruction evidence also stores direction, speed, and a host-side smooth-scroll value separately, then calls a native scroll-parameter path. This reinforces that device resolution and software smoothing are separate controls; it does not establish that Options+ exposes that flag for this mouse or prove its runtime effect. [Local static analysis, direction and smoothing](</Users/axatol/Workspace/ai/rea/investigations/logi-options-plus/pairing-buttons-scrolling.md#L59>)

If “stepped on-screen” means strict line snapping in every app, the current native-reporting slice does not establish that outcome. A future mouse-scoped diversion/translation path is a separate candidate requiring its own design and permission/routing/cleanup review; the current wheel contract excludes diversion, synthetic scroll and global preference changes. [Current contract](logitech-slice-contract.md#L25-L29)

## Evidence boundary and acceptance gates

The existing Bolt probe read `0x2121` at index 15, version 1, capability flags `0x1C`; it changed inversion mode 0→4, confirmed the opposite direction by operator report, and restored mode 0. This is bounded physical evidence for inversion only. It did not exercise resolution bit `0x02`, SmartShift, or ratchet behavior. The current spike register explicitly leaves SmartShift and high-resolution options open. [Wheel probe summary](</Users/axatol/Workspace/hans-m-song/logibridge/docs/research/wheel-v6-success-2026-10-19.md#L7>), [remaining hardware gates](</Users/axatol/Workspace/hans-m-song/logibridge/docs/research/remaining-spikes-2026-10-19.md#L10>), [reconciliation, U-07](</Users/axatol/Workspace/hans-m-song/logibridge/docs/research/options-plus-spike-reconciliation-2026-10-19.md#L41>)

The upstream source establishes feature function numbers and bit/setting mappings, but no exact byte-for-byte request/acknowledgement recipe has been demonstrated for resolution or SmartShift on this Bolt session. Treat those packet details, returned values, and state-transition semantics as unknown until a separately authorized physical check reads, writes once, and verifies the selected device.

Before calling the feature complete, use one explicitly selected Bolt slot and require: (1) fresh feature/version/capability discovery and baseline read; (2) an isolated resolution-bit change that preserves bits 0 and 2, followed by readback and manual comparison in the app where the user noticed the issue; (3) SmartShift mode and sensitivity read/write/readback, followed by physical checks of automatic, ratchet and free-spin behavior; and (4) verification that saved intent, observed mode and failed/unsupported states remain distinct. The single existing 15-ID-per-handle budget means do not send a write on every slider drag; stage the threshold locally and send once on release, then verify readback. [Bounded request policy](logitech-slice-contract.md#L29-L29), [same-handle 15-ID constraint](logitech-slice-contract.md#L38-L38)

The decisive limitation remains physical: high/low-resolution and SmartShift writes have not yet been demonstrated on this connection. Keep the visible copy honest about device input granularity until the line-stepping result is confirmed in the target application.

## Request-ID correction evidence — 2026-10-20

Owner’s failure screenshot says the bounded request-token budget was exhausted. Both production controller and IOKit worker previously consumed nonzero4-bit IDs permanently per slot/feature/function; existing injected tests deliberately reached failure and verified cleanup. This was a local lifetime policy, not an established device request allowance. [Logitech’s packet documentation](https://github.com/Logitech/cpg-docs/blob/master/hidpp20/README.rst#L58-L62) describes the echoed software identifier for correlation. [Linux’s upstream driver](https://github.com/torvalds/linux/blob/master/drivers/hid/hid-logitech-hidpp.c) serializes requests and uses its software identifier repeatedly; [Solaar’s request implementation](https://github.com/pwr-Solaar/Solaar/blob/master/lib/logitech_receiver/base.py#L610-L732) rotates software IDs for serialized requests. This corroborates reusable completion IDs; it does not guarantee arbitrary delayed duplicate behavior on the owner’s receiver.

Owner approved NX-12#428 to replace the lifetime policy with shared transport leases, successful-completion reuse, ambiguous-ID retirement and cleanup reserves (decision68). A new actual-controller regression failed before the change and passed after it; future native behavior is an owner gate.
